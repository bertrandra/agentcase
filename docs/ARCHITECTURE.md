## 1. Overview

AgentCase computes an agentic-transformation business case:

```
AS-IS team × rate card × SDLC/regulatory artefact scope
  → automation potential, glass ceiling, adoption ramp (S-curve)
  → TO-BE human FTE + agent vFTE
  → run cost, savings, NPV, payback
  → scenarios, Monte Carlo, strategy ranking, decision verdict
```

The build is React 18 + strict TypeScript (Vite 8, Vitest 5, Immer 10, Zustand 4, Chart.js 4.4.1, ExcelJS 4.4). `npm run build`
produces **one offline HTML file** (`app/dist/index.html`, about 2.7 MB with ExcelJS stored compressed, §9; `vite-plugin-singlefile` inlines script and style). The whole
case is one JSON document (`Doc`); the UI renders selectors over it and changes it only through commands.

| Property | Mechanism |
|---|---|
| Same numbers as the legacy app | oracle fixtures, §8 |
| Every business edit is undoable | one write path, `dispatch(command)`, §4 |
| Layers cannot be bypassed | ESLint `boundaries` + `no-restricted-imports`, §2 |
| No file over 150 lines | ESLint `max-lines` + `tests/size.test.ts` |
| No raw HTML injection | ESLint ban on `dangerouslySetInnerHTML`, content rendered by React elements, §9 |

## 2. Layers and the rules enforced by ESLint

```
ui/            React: shell, zones, sections, widgets       reads with @/store/hooks, acts through @/controllers/*
controllers/   the only code that dispatches commands       defineCommand + plain functions
store/         Immer document, history, persistence         no React except hooks.ts/simulation.ts (selectors)
domain/        pure calculation engine and catalogues       no I/O, no DOM, no store
```

Config: `app/eslint.config.js`. Path alias `@` → `app/src`.

| Rule | Where | Effect |
|---|---|---|

## 3. Domain: the calculation engine

All of it is pure TypeScript over a `Ctx` built from the document (`makeCtx(doc)`, `src/domain/ctx.ts`). It runs in Node, so every
financial figure is testable without a browser.

- **Inputs seam.** The legacy `readInputs()` → `P()/V()/C()` seam is the specification of the inputs. Form values live in
  `doc.dom.values` / `doc.dom.checked` (strings and booleans, exactly as the legacy snapshot stores them); `src/domain/inputs.ts`
  parses them to numbers at the edge. The legacy DOM element ids remain the parameter namespace of the document.
- **Entry point.** `computeCase(state)` (`src/domain/index.ts`) returns `{ model, headline, payback, npv, phaseScope, glassCeiling }`.
  `useCaseResult()` memoises it per document identity.
- **Model.** `modelRaw(ctx)` is the flat annual computation (team cost, automation potential, glass ceiling, engagement and knowledge
  hub coefficients, ramps, setup, tokens, infrastructure, run team, verification tax, loops). `model(ctx)` (`model/overlay.ts`)
  calls `modelRaw` and, unless the active curve is the legacy flat one, overwrites the annual arrays with the Time Engine's year rows.
  Effective automation applies the human share once: `min(100 − ceiling, potential × posture × context × hub)` (legacy v18.11).
- **Time Engine** (`src/domain/time/`, replaces legacy `TIME`). Four layers as in the legacy: curve adapters (`adapters.ts`, `spline.ts`:
  spline / logistic / Gompertz / Bass / legacy flat), derivation kernel (`kernel.ts`, built from the raw model by `buildK`), path
  accumulator (`engine.ts`: cumulative, payback), aggregation (`years.ts`, `rows.ts`), plus `thin.ts` (row-free aggregate for Monte
  Carlo draws) and `fit.ts`. `canonical.ts` exposes `engineNow`, `paybackMonthsCanonical` and `npvCanonical` (discount rate from
  `MODEL.CASE.discountRate`, default 8 %): the single source for payback and NPV. The engine is always built from the raw model.
- **Discounted-cash-flow kernel** (`domain/economics/cashflow.ts`, zone *time-engine*, owner of the payback-month, NPV and ROI figures). The one place
  where a monthly cash-flow becomes a cumulative (`cumulativeOf`), a payback month (`paybackMonthOf`: the month after the last month >= `firstMonth`
  whose cumulative is < 0, null when the final cumulative is < 0, DEV-PAYBACK-RECOVERY; `displayedPayback` is the one shown payback), an NPV (`npvOf`: month t discounted by (1 + r/12)^t, or by (1 + r)^(t/12) with `compounding: 'annual'`), a discount factor and an ROI
  (`roiCanonical`); `cashflowSummary(net, { annualRate, firstMonth, compounding })` returns all of them. `DEFAULT_DISCOUNT_RATE` (0.08) is the only
  literal of the default rate. Callers: the Time Engine (`engine.ts`: path, `npv`, `roi`, `headline`), the Monte Carlo thin pass (`thin.ts`, used by
  `model/mcs.ts`), the portfolio summary (`portfolio/headline.ts`, payback not before the first movement), the legacy-mode audit (`pdc/verifConvTime.ts`,
  8 % as the legacy), the time-to-market value (`model/flow.ts`, annual compounding, the legacy P5 rule) and the cost-model discount factors. Lot 4
  replaced six inline loops by it; `tests/domain/cashflow.test.ts` compares it bit for bit (`Object.is`) with verbatim copies of those loops on random
  cash flows (fast-check), and every figure of the 107 fixtures and the portfolios was dumped before and after at full precision: identical.
- **Horizon.** `horizonYears()` (`model/horizonYears.ts`) returns one savings and one run-cost entry per horizon year; Monte Carlo,
  strategies and Results use it, so horizons 1 to 10 work (legacy v18.12/v18.13 fixes).
- **Portfolio** (`src/domain/portfolio/`, multi-product phase P1, spec [SPEC_MULTI_PRODUIT.md](SPEC_MULTI_PRODUIT.md)). Pure layer above `computeCase`,
  not yet wired to the store or the UI. `resolveProduct` builds a product's effective `CaseState` (common + whitelisted overrides + knowledge subset +
  own team; memoised on object identities), `runOf` runs the existing Time Engine once per resolved case, `consolidate` shifts each product's monthly
  rows onto the calendar and sums them (no formula of its own; ROI via `roiCanonical`, discount via `caseDiscountRate`), `envelopeCase` /
  `portfolioToCase` wrap and unwrap a single case.
- **No module state** (lot 5a). A domain function's result depends on its arguments only: no module-level `let` (the last global was the theme in
  effect, `setActiveTheme()` / `setDisplayTheme()` / `setActiveThemeDef()`, read by `tok()` in 16 domain and 2 store modules, so a read-out or an export
  depended on whatever theme was set last). A read-out that only chooses a colour MEANING returns a colour **role** (`ColourRole`, a token name:
  `riskBand(s).tone = 'danger-800'`, `VERDICT_META[v].tone / bgTone`, readiness and HRI bands, eligibility, scenario, sensitivity-cell, Gantt and
  pipeline-timeline tones), which the UI resolves in the theme in effect; `groupColor()` takes its fallback (the UI passes the theme's `slate-600`, the
  parameters workbook keeps the data default). The memo caches (WeakMaps keyed by a context, a case or a portfolio) stay: same input, same output.
  `tests/domain/no-module-state.test.ts` enforces it (§ 2).
- **Stress** (`stress/`): scenarios, sensitivity, seeded Monte Carlo (`rng.ts`, `simulate.ts`), strategies, `fingerprint.ts` (a hash of
  the model inputs only, to decide whether a stored distribution is stale).
- **Verification** (`pdc/verifChecks.ts` and `verifConv*.ts`): the 16 automatic checks and the 67 convergence rows of the Logic
  verification section, as pure functions over a `Ctx`.

Scope re-fit: with *Fit to selected scope* on, the potential follows the scope's effort-weighted automatable share. `store/derive.ts`
`refitPotential(draft)` is called by every command that changes the scope (SDLC artefact selection, industry, norms, cross-cutting,
regulatory catalogue, import).

## 4. Store: Immer patches, commands, history

`src/store/core.ts` creates one store (`zustand/vanilla`) holding `{ portfolio, doc, history, audit, rev }`. Since multi-product P2 the
**source of truth is the `Portfolio`** (`domain/portfolio`: `common` = every key of a case except `teamIn`, `products`, `waves`, `activeProductId`,
`hub`, `horizonMonths`; `docs/SPEC_MULTI_PRODUIT.md`). `doc` is **derived**: `deriveDoc(portfolio)` = `resolveProduct(portfolio, activeProductId)`,
the active product's effective case, identity-stable while its inputs are (P1 memo). Everything written for a single case (the ~200 commands, the 79
sections, `useDoc`/`useCtx`/`useCaseResult`, `toSnapshot(doc)`, the Excel and report adapters) reads and writes `doc` unchanged. History, audit,
autosave and broadcast patches are on the **portfolio**.

```
dispatch(command) ──► ONE produceWithPatches(portfolio) ──► patches + inverse patches
                           (case command: run on a draft of the derived doc, then the ADDRESS LAYER maps each change to the portfolio)
                           └─► history.pushEntry (coalescing, cap) ──► audit log ──► listeners (autosave, broadcast)
```

| Concept | Implementation |
|---|---|
| Command | `{ type, payload, label, coalesceKey?, undoable, run(draft, payload), runPortfolio? }`. Case commands use `defineCommand` (`store/commands.ts`): `run` mutates the active product's effective case. Portfolio commands use `definePortfolioCommand`: a pure `apply(portfolio, payload)`, turned into minimal Immer patches by `store/syncDraft.ts`. <!-- fact:commands -->286<!-- /fact --> commands are registered by the modules of `src/controllers` (<!-- fact:undoable -->282<!-- /fact --> undoable; <!-- fact:viewCommands -->4<!-- /fact --> view commands - `view.setPersona`, `product.setActive`, `product.setEditScope`, `portfolio.setDisplayScope` - are applied but never on the undo stack; counted from `COMMAND_REGISTRY` after loading the controller modules; <!-- fact:portfolioCommands -->27<!-- /fact --> of them are `product.*` / `wave.*` / `portfolio.*`, the others include `excel.importPortfolio` and `snapshots.activatePortfolio` / `baselinePortfolio`); a duplicate type throws |
| Address layer | `store/address/` (`index.ts`, `dom.ts`, `subset.ts`). After a case command ran on the derived doc, each changed top-level key is re-addressed onto the portfolio inside the same produce: `teamIn` -> the active product's `teamIn`; a whitelisted key (spec 4.3) -> `product.overrides[key]` if the product already overrides it OR the edit scope is `'product'` (and the value differs from common), else `common[key]`; a changed form field of `dom.values` / `dom.checked` is routed per field (Knowledge Hub fields to the product's knowledge subset when it defines them, then override/common by the same rule; `horizon`, `khInfraMonthly`, `khEnabled` mirror into `horizonMonths` / `hub`); any non-overridable key (RATE, MODEL, COEF, PERSONAS, nav, snapshots, customerName, ...) -> `common`. With one product and no override the result is exactly today's behaviour |
| View state | `activeProductId` (saved with the file, D-M6), `editScope` (`'all'` / `'product'`, transient, never saved), `displayScope` and `persona` change through `undoable: false` commands (`product.setActive`, `product.setEditScope`, `portfolio.setDisplayScope`, `view.setPersona`): applied, logged, never on the undo stack, filtered out of broadcast patches (`VIEW_FIELDS`); the store also strips them from every undoable step (`batch`: a snapshot activation or a File > Open never carries the view into its undo entry), so undo / redo never move the view. After an undo/redo/remote patch an unknown active product falls back to the first one (`normalizeActive`) |
| Persona = view state of the tab (lot-3 decision D3) | `PortfolioDoc.persona` (`store/persona.ts`), read with `usePersona()`. Switching it in one tab never reaches another tab, never enters the history, and an undo never moves it. The case never holds it: `makeDefaultDoc`, `fromSnapshot`, `readPortfolio` drop the legacy `currentPersona`, and `commit` drops a stray one (an old snapshot activated, a patch from an older build). Files keep the legacy key as **the persona the file opens on**: written from the saving tab's persona as the first key of the case (or of `common`), read back by `openChecked` (absent: `builder`), applied by `load` outside the undo step (undoing an open keeps the persona). The persona-only JSON companion of the parameters workbook names the tab's persona, like the legacy. A portfolio replacing the current one (portfolio import, snapshot activation, another tab's document) keeps the tab's persona, edit scope and display scope (a Wave view while that wave exists) (`keepTabView`). A tab whose persona another tab deleted shows Advanced |
| Edit base (lot 3) | THE RULE: a value a command writes is computed from the case the command RUNS ON. `runCommands` runs a case command on `editBaseOf(pf)` (`store/portfolioState.ts`): the common case (`commonEditDoc`) with "Change: All products" in a Portfolio / Wave view (`editsCommon`), else the active product's effective case. So read-then-compute lives inside `run(draft)` (e.g. `pdc.setDdSensitivity` measures `current(draft)`); a controller that needs the case before dispatching (validation, labels, before / after) reads `editBase()` (`store/editBase.ts`), never the store's derived `doc` (the ACTIVE product, whose overridden values would leak into the common ones). `activeDoc()` is the active product's case for what is explicitly about it (exports, file names, the results' Monte Carlo runs, a snapshot capture). Enforced by ESLint in `src/controllers` (§ 2); `tests/store/edit-base*.test.ts` check each controller on a 3-product portfolio where the active product overrides the field |
| High-water marks | `HIGH_WATER_KEYS` (`THEME_SEQ`, the last theme sequence id issued): counters that never go back. `commit` re-raises them after every do / undo / redo / remote patch (not when a document is opened), outside the history; they are common keys, hence saved and kept across a reload. So a theme id is never issued twice (create, undo, create gives 101). An undo restores everything else exactly (`snapUndoable` in the registry test) |
| Portfolio commands | `controllers/product.ts` (add, rename, duplicate, archive, remove, setNote, setOffset, setActive, setEditScope), `productOverrides.ts` (setOverride, clearOverride, applyToCommon, setKnowledge), `wave.ts` (add, rename, remove, reorder, setStart, setNote, assign), `portfolio.ts` (setHorizon, setHub, setRho), `stressPortfolio.ts` (run, not a command). `portfolioGuard.dispatchChecked` refuses (returns false, no step) any command whose result breaks `validate` (last product, weights != 100, 50-product cap, ...) |
| Registry | `COMMAND_REGISTRY` (type, undoable). `tests/store/registry.test.ts` fails if a command has no sample in `tests/store/samples/`, no label, or does not round-trip through undo/redo, both on the default case and on a 3-product, 2-wave portfolio (view commands with `undoable: false` must add no step) |
| History | `undo` / `redo` stacks of `{ label, type, ts, coalesceKey, patches, inverse }`. Cap `HISTORY_CAP = 200`. A new step clears redo |
| Coalescing | consecutive entries with the same `coalesceKey` inside `COALESCE_MS = 800` merge into one step (slider drags, typing in a number field) |
| Transactions | `batch(label, commands, coalesceKey?)` is one step: bulk edits, imports, applying a strategy |
| Jump | `jumpTo(index)` (History panel) undoes or redoes until `index` steps remain |
| Open a case | `load(doc, keepHistory)`: by default a fresh history (`controllers/openFile.ts` decides); `keepHistory` makes it one undoable step |
| Remote patches | `applyRemote(patches)` applies a patch from another tab, logs it, never pushes it on this tab's undo stack |
| Audit log | ring of the last 500 records `{ ts, type, label, kind: do/undo/redo/remote/load }` kept in the store |
| Derived data | never in the document or the history: `useCaseResult`, `useCtx` (WeakMap memo on document identity); the Monte Carlo run lives in `simStore` (`store/simulation.ts`) with a fingerprint, so a verdict is marked stale when the case moves |
| UI state | `ui/uiState.ts`, a separate store: current section, persona-menu mode, wizard, toasts. Not undoable (decision D4) |

Consequences of the layering: the UI cannot import `dispatch`, so Ctrl/Cmd+Z (handled in `ui/shell/useShortcuts.ts`; text fields keep
their native undo) covers every business input by construction. `tests/store/undo-property.test.ts` (fast-check) checks random
command sequences against `undo∘apply = id` and symmetric redo; `tests/store/portfolio-undo.test.ts` does the same on a 3-product portfolio with case, product, wave, override and scope commands mixed (A6), checking `validate` after every step.

## 5. Persistence

All adapters live in `src/store/persistence/` and `src/controllers/` (file and boot wiring). The case keeps the **legacy snapshot
state** (the same registry keys), so old files load. Two file formats coexist (`persistence/portfolioSnapshot.ts`):

- `agentcase.snapshot.v1`, one case. Opening it **envelopes** it (F21): `envelopeCase` = "Product 1" in "Wave 1" at month 0, identical numbers (A1 on the 107 fixtures through the real open path, `tests/store/portfolio-a1.test.ts`).
- `agentcase.portfolio.v1`, a portfolio (`readPortfolio`: `sanitize`, safe ids `[A-Za-z0-9_-]{1,64}`, shapes checked, `validate` invariants enforced, common values filled from the code defaults). **Save rule (F22, `isSingleCase`)**: a portfolio is written as `snapshot.v1` exactly when that file re-opens to the very same portfolio (one product, one wave, no override, no knowledge subset, default names/ids/offset); anything else, incl. a renamed product, keeps the portfolio format so a save never loses information. Hence existing file/HTML/Excel tools and tests keep seeing v1 files for single cases, and export -> open of a single-product portfolio is identical (A9).

The autosave record is the exact portfolio (`full` mode, never collapsed to v1) plus its history, because the undo patches address product and wave positions; a record without `format: 'portfolio'` (written before P2) restores its document but not its case-level history.

| Adapter | Files | Behaviour |
|---|---|---|
| Snapshot JSON | `snapshot.ts` | `toSnapshot` adds `savedAt`, `_schema: 'agentcase.snapshot.v1'` and `_schemaVersion`; `fromSnapshot` deep-copies through `sanitize` (drops `__proto__`, `constructor`, `prototype`), requires the form inputs (`dom`), and fills missing keys from the code defaults so new defaults reach old files |
| File schema, migrations, validation | `schema/` (`version.ts`, `caseChecks.ts`, `portfolioChecks.ts`, `index.ts`) | see "File schema" below |
| Autosave | `autosave.ts`, `idb.ts` | debounced (1.5 s default) record per tab `{ tabId, savedAt, label, snapshot, history }` in IndexedDB `agentcase-v19` (store `autosave`), so Ctrl+Z survives a reload (decision D5). `memoryStorage()` for tests. After each save the records beyond `AUTOSAVE_CAP` (20, the Sessions list cap) are pruned, oldest first (every page load is a new tab id). A failed save never throws: the user is told once per failure streak (a toast). The record keeps its calculation packages: the restore compares them with the recomputed figures (staleness banner after an engine change). `restoreRecord` puts the history back only for a record of the current file schema (a migrated one may have changed the shape its patches address) |
| Boot | `controllers/boot.ts`, `src/main.tsx` | opens an embedded case before the first paint, then offers the newest autosave of another tab that is **newer than the file's own `savedAt`** (never auto-restores) |
| Multi-tab | `broadcast.ts` | `BroadcastChannel('agentcase-v19')`: local changes are posted as patches (the inverse for an undo) with the sender's file schema version `v` and its sync identity (`SyncId`: a document id, new at every open, and a revision); a patch is applied with `applyRemote` only on the same document at the revision it was made on, never on another document. Opening a document (file, session, autosave restore) posts it whole: the other tabs replace theirs (`replaceRemote`, keeping their view state). Another revision of the same document is a divergence: the tab behind (lower revision, then lower tab id) takes the other's whole document (`request` / `full`). A patch that does not fit is refused whole (`applyRemote` never throws) and the document is requested. A remote change that moves products or waves, or a replacement, clears the local undo / redo (their patches address positions), with a toast (`controllers/notices.ts`). A message from a tab of another schema (newer, or older since v3: its patches address the version 2 scope keys), or without a document id (an older build), is ignored; a whole document carries its process documents as XML text, patches address nodes of the tree |
| HTML snapshot | `html/embed.ts`, `read.ts`, `legacy.ts` | the running page is cloned, `#root` emptied, transient nodes dropped, the case embedded in `<script type="application/json" id="agentcase-snapshot">` with `<` and the JS line separators escaped; re-saving replaces the script. File name `AgentCase_<customer>_<vTag>_Snapshot_<stamp>.html` |
| Re-fit on open | `controllers/openFile.ts#refitOnOpen`, `store/derive.ts#refitPortfolio` | like the legacy `applySnapshotState`, a restore re-runs the scope fit; used for file open, the embedded case and snapshot activation (not in `fromSnapshot`). For a portfolio every product's potential follows ITS effective scope (most frequent value shared as common, others as overrides); edits re-fit the active product only, as before |

**File schema.** Every file written (JSON, HTML snapshot, autosave record) carries `_schemaVersion: SNAPSHOT_SCHEMA_VERSION` (3); a file without it is v1 (all files
up to v20.12; legacy v18.x files too). v2 -> v3 (BPMN B3, § 14) writes the case's process document `BPMN` from its nine scope keys and removes them (portfolio:
common document, whole-document product overrides; snapshot library converted); the document is XML text in the file and is read by the B2 reader in the
validators (unreadable: a correction note, default process). Every open path (file menu, Import / Export, HTML snapshot, embedded case at boot, autosave restore, sessions) goes through
`openChecked(raw)` (`schema/index.ts`): `sanitize` -> `migrate` (the chain `MIGRATIONS[n]`: vn -> vn+1, pure functions on the raw JSON; v1 -> v2 is a no-op for
every file this app or the legacy wrote, it only normalises a hand-edited portfolio tag; v2 -> v3 writes the process document) -> light hand-written validators (no schema library) -> the strict readers
(`fromSnapshot` / `readPortfolio`, unchanged). Validators (`caseChecks.ts`): `MODEL` (blocks are objects, scalar settings keep the default's type), `RATE` (location -> grade
-> day rate >= 0), `teamIn` rows (objects, FTE a number >= 0, text skill / grade / location), `PERSONAS` / `GROUPS` / `sectionGroups` (entries with a text id), `THEMES` /
`THEME_SEQ`, form inputs. Portfolio structure (`portfolioChecks.ts`): products (safe unique ids, name, team, knowledge subset fields, override whitelist and forbidden
fields, offset), waves (safe unique ids, start, one wave per product, `waveId` agreeing with the lists), active product, hub, horizon, `rho`; every invariant
`readPortfolio` / `validate` enforce is made true. A damaged value is replaced by the default (or dropped when optional) and a note is collected; the open
succeeds and `controllers/openNotes.ts` holds the notes, shown by `ui/shell/OpenNotesBanner.tsx` (toast "Opened with N corrections", then a `role=status` notice
listing them, Dismiss). An autosave record that needed corrections comes back without its history (its patches address the uncorrected document). Unknown
top-level keys are carried through (forward compatibility), as before. Only three things are refused: not a JSON object, an object with neither form inputs nor
the portfolio tag (not an AgentCase file), and a file of a newer schema (`NewerFileError`: "This file was made with a newer AgentCase (file format vN; this version
reads up to v3)…"). `tests/store/schema-versions.test.ts` opens every committed case file (115) with no correction and the same work as the migration chain and the strict readers alone;
`schema-corrections.test.ts` covers damaged cases and portfolios. Adding a version: bump the constant, add `MIGRATIONS[n]`, test that old files still open the same.

Every saved case (JSON, HTML snapshot, autosave record) carries the canonical calculation package `{schemaVersion, calculationVersion, inputHash, curveModelId, headline, annual}` (`domain/calcPackage.ts`, stamped by `toSnapshot`, dropped by `fromSnapshot`: it is never part of the document). On open, `controllers/calcStaleness.ts#checkLoadedCase` recomputes the package and compares it (`domain/calcStaleness.ts`: valid / stale / versionMismatch / notCalculated; figures to 1e-6). A portfolio file stamps `calculationPackages: {[productId]: package}` (each product's resolved case, exactly the single-case package) plus a portfolio-level `calculationPackage` (`inputHash` `pf1:`, consolidated headline and calendar-year table from `domain/portfolio/package.ts`); `checkPortfolioStaleness` compares both levels, worst state wins, `staleProducts` names the products that moved. A mismatch shows the legacy banner (`ui/shell/CalcStaleBanner.tsx`, `role=status`, Dismiss). The banner state lives in the controller, outside the document and the undo history; files without a package (older fixtures) open silently. Figures are always recomputed from the inputs, the package is only compared. The Excel workbooks already read the same engine, so they equal the package figures without change.

**Error boundaries** (`ui/errors/`). A render, lifecycle or effect error of a React subtree is caught at three levels, so one failure never blanks the app:

| Level | Where | Fallback |
|---|---|---|
| App | `App.tsx`, around the whole shell | a minimal page that needs neither the store nor the theme runtime: "AgentCase hit an unexpected error", **Reload**, **Copy details**; it writes the autosave at once (`flushAutosave()`, `controllers/boot.ts`), and the reload offers to restore that record (the restore banner) |
| Section | `zones/SectionHost.tsx`, inside `<main>`, around the section (and its in-place editor) | in the work area: "This section failed to display", **Try again** (drops the cached `React.lazy` component and remounts the boundary), **Copy details**; the menu, KPI bar, dock and every other section keep working. The boundary is keyed by section id, so opening another section resets it |
| Chart | `widgets/ChartPanel.tsx`, around every Chart.js canvas | a note in the chart's place (same height): the figures and tables of the section are unaffected; a new chart config tries again |

**Copy details** puts the app version, the scope and place (section id or chart label), the time, the message, the stack and the component stack on the
clipboard (the text also stays readable in a *Details* disclosure where the clipboard is blocked). Every caught error is written to the console and kept
in a small in-memory list (20 entries, this session only, never in the case) that the dock shows ("History (n) · 1 display error"). The case itself lives
in the store, outside React, so a display error never changes it. Errors of event handlers and timers are not render errors and keep their own
messages (toasts, status lines). Tests: `tests/ui/error-boundaries.test.tsx` (a throwing section, Try again, navigation reset, Copy details, the dock list,
a throwing chart, the app page, axe on each fallback); `tools/e2e-smoke.mjs` also fails when a section shows the fallback.

**Theme tokens.** No component holds a visual literal: colours, fonts, sizes, weights, line heights, radii, border widths, shadows,
control paddings and durations are tokens (`docs/THEME.md`). The table lives in `domain/theme` (zone `presentation`, so the store's Excel
and report exports can read it); `ui/theme/tokens.css` is generated from it (`npm run theme:gen`, checked by `tests/ui/theme-tokens.test.ts`).
CSS, inline styles and SVG attributes use `var(--ac-*)`; chart.js and colour arithmetic use `tok()` of the theme in effect (`useTheme()`); Excel uses
`argb(print, name)`. `tests/ui/no-hardcoded-style.test.ts` keeps literals out.
**Theme axes (T3)** — shape, box style, density, typography and control variants — are closed value lists in `domain/theme/axes.ts`
(token sets in `variants.ts`, `typography.ts`; the new defaults in `layout.ts`). Each value is a `data-ac-<axis>` attribute on `:root` (or on
a preview container) selecting a block of the generated `ui/theme/axes.css`; `axisTokens()` gives the same values to the base table of a theme (`themeBase`).
`ui/themeAxes.ts` writes and reads the attributes (`applyThemeAxes`, `useThemeAxis`); the shared `ui/widgets/field/Field*` controls read the
three control axes and render a slider, stepper, segmented / radio group or switch that dispatches the same command as the native control.
**Display modes** (dark, contrast standard / enhanced / high, colour-blind safe
charts, reduced motion) are value sets over the base theme in `domain/theme/modes.ts`: generated as CSS blocks keyed by `data-ac-*`
attributes on `<html>` (tokens.css). The viewer's preference is view state in `ui/display`
(localStorage `agentcase.display`, never in the case, never undoable; "auto" follows `prefers-color-scheme` / `prefers-contrast`).
The printed exports (Excel, HTML report) read the print theme, the base theme without any display: always light.
`tests/ui/theme-contrast.test.ts` checks every text / background role pair in each mode x level (docs/THEME.md §7).
**Theme library and brand (T4 + T5).** A case carries a theme library (`domain/theme/library.ts`: seven protected built-ins in

## 9. Security properties

| Property | How it is enforced |
|---|---|
| No raw HTML | `dangerouslySetInnerHTML` is a lint error; `grep` finds no `innerHTML`, `eval` or `new Function` in `app/src`. React escapes text and attributes; `Rich` accepts only whitelisted tags/attributes; colours must match `#hex` |
| Hostile snapshots | `sanitize` drops prototype-pollution keys at every depth; the legacy HTML restore script is parsed as JSON, never executed; unknown shapes are rejected |
| Embedded case | `<` and U+2028/2029 escaped in the embedded JSON, so `</script>` or `<!--` in a customer name cannot break out |
| Hardened workbook import | `excel/params/safe.ts`: limits (file 8 MB, unzipped 64 MB, 400 entries, compression ratio 200, 20,000 rows, 64 columns, 5,000 chars of text), `safeId`, `cleanText`, `okKey`; a file that fails leaves the case untouched |
| No network | the build has no runtime fetch; fonts and libraries are inlined |
| Content-Security-Policy | `app/index.html` declares, first in `<head>` (before the inlined script), `default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data: blob:; font-src data:; connect-src 'none'; media-src data: blob:; base-uri 'none'; form-action 'none'`: the page can load nothing from the network, even if a bug or a hostile file tried (images and fonts only as `data:` / `blob:`: the logo, the inlined Ubuntu faces; no worker, the Monte Carlo runs on the main thread; no `eval`, so no `'unsafe-eval'` / `'wasm-unsafe-eval'`). `'unsafe-inline'` is needed because `vite-plugin-singlefile` inlines the one script; a hash would change with every build. The compressed ExcelJS (D5, § 10) is started as an inline classic `<script>` built from the decompressed text, which `'unsafe-inline'` already allows: no `blob:` script source was added (a blob-URL module import would have needed `script-src blob:`, which lets any blob the page creates run as code), and the element is removed once it ran. `frame-ancestors` cannot be set by a meta tag (browsers ignore it there): framing protection needs an HTTP header, which a file opened from disk does not have. The dev server (`vite`, serve only) drops the meta for its module scripts and HMR socket. A saved HTML snapshot clones the page, so it carries the same policy; the two reports (`report/render.ts`, `REPORT_CSP`) carry a stricter one (no script at all, inline style, `data:` logo). `tests/csp.test.ts` checks the three; `tools/e2e-smoke.mjs` fails on any `securitypolicyviolation` event, and `tools/e2e-flows.mjs` drives every file / canvas / long-running flow (JSON and HTML snapshot round trips, report, the three workbooks and the import, Monte Carlo, themes, PNG and SVG logo, `?theme=` link) under the policy, after a probe proving that a network image and a `fetch` are blocked |
| Dependencies | `npm audit --omit=dev --audit-level=moderate` runs in CI (job `check`): 0 advisories. Third-party licence of note: bpmn-js (phase B6, the optional BPMN editor) is MIT with a clause that its bpmn.io watermark must stay fully visible and not be covered; the app never hides it (tests/ui/sections/process-editor.test.tsx, tools/e2e-bpmn-editor.mjs). ExcelJS 4.4 depends on `uuid` 8 (GHSA-w5hq-g745-h8pq, moderate, a bounds check of `v3`/`v5`/`v6` with a caller buffer); `app/package.json` `overrides` pins `uuid` to `^11.1.1`, which keeps the CommonJS `require('uuid').v4` that ExcelJS's Node build calls (the Excel tests run on it). The browser build uses ExcelJS's own pre-bundled `dist/exceljs.min.js`, which embeds its copy of `uuid` and calls only `v4()` without a buffer: the vulnerable path is not reachable there |
| Display errors | error boundaries (§ 6, *Error boundaries*): a render error shows a fallback instead of a blank page; the case (in the store, outside React) is untouched and still autosaved |

## 10. Performance notes

- Derived values are computed once per document identity (WeakMap memo) instead of per render; the Monte Carlo run is separate and marked stale by a fingerprint of the model inputs, so a re-render never re-runs it.
- Patch-based history stores only changed paths (cap 200 steps, plus the autosave record).
- Sections are loaded with dynamic `import()`; the single-file build still inlines them (the build log lists one JS and one CSS file), so this changes evaluation order, not download size.
- **ExcelJS stored compressed (decision D5, lot 5a).** ExcelJS was about 940 kB of the 3.2 MB file, parsed at every boot though only an Excel import or export
  uses it. The build (`vite.config.ts`, plugin `excelPayload`) replaces `excel/excelSource.ts` by a module holding ExcelJS's browser bundle
  (`exceljs/dist/exceljs.min.js`, the same UMD file the bundle used to inline) gzip-compressed and base64-encoded (342 kB). On the first Excel action
  `excel/excelInline.ts` decompresses it with the browser's `DecompressionStream`, runs it as an inline script (removed at once; the UMD global is taken
  and deleted) and caches the module for the session. Measured on this build: `dist/index.html` 3,279,804 → 2,682,700 bytes (−18 %), gzip 992,033 →
  979,213 bytes, time to the shell 586-620 → 317-345 ms; first Excel use adds the decompression (a few tens of ms). `tools/e2e-flows.mjs` checks on the
  BUILT app that nothing of ExcelJS is in the page before the first export nor after it, and every workbook export and import (and `tools/parallel-run.mjs`,
  40 workbooks) runs through it. Needs `DecompressionStream` (Chrome 80, Firefox 113, Safari 16.4); an older browser gets a message on the Excel action.
- **The BPMN editor stored compressed (phase B6, docs/SPEC_BPMN.md § 9.2).** The same pattern for bpmn-js (pinned 18.31.0): plugin `bpmnPayload` replaces
  `controllers/processEditorKit.ts` by one gzipped base64 string marked `agentcase-bpmn-js:` (the modeler's UMD bundle and its style sheets, 0.27 MB);
  `controllers/processEditorInline.ts` runs it on the first "Edit diagram" of the Process section. `tools/perf.mjs` measures the app without that string
  for the regression budgets and the string against its own budget (`bpmnPayloadMB`); `tools/e2e-bpmn-editor.mjs` checks on the built file that nothing of
  bpmn-js runs before the editor opens, no CSP violation, the bpmn.io watermark visible, one undoable save. The editor's saves go through the B2 reader and
  `domain/process/editorMerge.ts` / `editorApply.ts` (a merge into the stored tree that keeps unchanged nodes) as the command `process.applyEditor`.
- **Re-render cost (lot 5a).** One edit renders far fewer components (§ 6, *Selector hooks*: 706 → 415 over the 12 measured runs); `tools/perf.mjs`
  edit → KPI repaint median 21-22 → 16-18 ms, p95 32-35 → 25-31 ms.
- Multi-product (P4): consolidation view model ~4 ms and a 20-product team edit ~25 ms end to end (all views) on a 20 x 60-month portfolio, budgets 30 ms / 150 ms in `tests/domain/portfolio/perf-p4.test.ts`.
- Size: `dist/index.html` 2.80 MB (2.67 MiB, about 1,020 kB gzip) at the last local build (lot 10: chart.js registers only the controllers, elements,
  scales and plugins the app draws with, -11 kB). `app/perf-budget.json` holds two size budgets: the hard product ceilings `sizeMB` 5 / `gzipMB` 1.5 (MiB,
  never rewritten by the script) and the regression budgets `sizeRegressionMB` / `gzipRegressionMB` (1.15 x the measured build, 3.08 / 1.12) that fail on
  growth; and the time budgets of the shell, an edit, an undo (until the headline bar repainted), and the section switches (until the TARGET section's
  heading is shown; single case and the six Portfolio sections on the shipped example), max(floor, 3 x measured). `tools/perf.mjs` checks them (CI job
  `e2e`) and fails when the file is missing; `--write-budget` re-baselines.

## 13. Calculation zones, the generated dependency graph and test selection

Layers say *where* code may live; **zones** say *what it computes*. They exist so that "one source of truth, no duplicated calculation" is checked by a test
instead of remembered, and so that the tests a change needs can be found from the code. Nothing here adds a calculation: the numbers are the oracle's.

**Zones.** `app/src/domain/zones/catalog.json` lists <!-- fact:zones -->20<!-- /fact -->: <!-- fact:inputZones -->6<!-- /fact --> input zones (rate card and team, scope and automation potential, process model (BPMN), adoption curve, Knowledge Hub, run sizing /
setup / taxes), <!-- fact:calcZones -->4<!-- /fact --> calculation zones (Time Engine and annual model, readiness and programme tuning, stress, product resolution), <!-- fact:resultZones -->8<!-- /fact --> result zones (economics headline,
delivery views, verdict, evidence and due diligence, logic verification, portfolio consolidation, aggregated views, exports, workspace and configuration) and <!-- fact:sharedZones -->2<!-- /fact --> shared ones (foundation, presentation
formatting), each with a lane, a description, entry modules and the figures it owns. They follow the code, not the menu: a module that *reads* the engine to print
something (the run-sizing read-out, the glass-ceiling impact chart) belongs to *delivery views*, not to the zone whose inputs it shows, which keeps the
domain zone graph **acyclic** (lot 4; it had one cycle of 15 zones before). A module is tagged by its role, not its folder: the cash-flow kernel lives in
`economics/` but computes for the engine (*time-engine*); `model/flow.ts`, `scope/scurveView.ts`, `pdc/verifTeam.ts` and `domain/index.ts` (`computeCase`, the KPI bar)
are read-outs (*delivery-views*); `tune/maturity.ts` is programme tuning; the portfolio knowledge views and diagnostics are consolidation; the verdict, the
evidence ladder and the due-diligence register (*verdict*) are read by the Board registry, which the logic checks (*verification*) audit in turn.

**Tags.** The first line of every module under `src/domain`, of every controller, of the export modules (`store/persistence/{excel,report,html}`) and of the zone hooks of
`src/store` is `/** @calc-zone <zone-id> */`, plus `@owner <figure-id>[, ...]` on the module that owns a figure. `tests/domain/zones-tags.test.ts` fails when a module has no valid tag, when
an `@owner` names an unknown figure, when a figure has no owner or two, when the owner is in another zone than the catalogue says, or when an entry module is missing.
A figure (the catalogue lists <!-- fact:figures -->23<!-- /fact -->: net, ROI, payback month and year, NPV, total benefit, saving %, setup, baseline and run cost, savings per year, effective automation, glass ceiling, verification tax,
FTE before / after, velocity uplift, KPI scorecard, decision verdict, Monte Carlo distribution, portfolio headline, ...) is therefore computed in one module; every other screen,
export and report imports it. `tests/domain/figure-owners.test.ts` proves it on the fixtures: the same figure on the KPI bar, Results, Financial, the Board variables, the calculation
package, the Excel results workbook, the report and the consolidation equals the owner's value. `npm run dup` (jscpd, threshold at the current level) catches a copy of a block.

**Generated graph.** `npm run deps:gen` (`app/scripts/gen-deps.ts`, TypeScript compiler API, syntax only, about 2 s) writes `app/src/generated/dependencies.json` (committed, about 75 KB):
zones, sections (kind from `sectionScope.json`), edges and the zone set of every test. Rules: type-only imports are not edges; a barrel of `src/domain` is followed by symbol
(`import { x } from '@/domain/stress'` is an import of the file that declares `x`); **zone edges are per layer and count uses only**: the domain zone graph (`edges`, kind `z`)
is built from the imports of `src/domain` modules, re-exports (`export … from`) and pure barrels (modules made only of re-exports) create no zone edge, and the zone links of
the controllers and the store exports are reported apart (`outer`, never part of the build order); the re-export edges stay in the import closure, so test selection still
follows a namespace import through a barrel; `store/hooks.ts` is a generic accessor whose heavy symbols are routed to their domain
owner (`graphConfig.json`); the shell, the frame and the View-selector widgets are on every screen and are on the ignore list, with a reason; the shared zones create no edge.
A section reaches a zone when the import closure of its folder, walked through untagged ui / store modules, hits a tagged module (`r`, read: the zone feeds the section; `w`, write:
an input section reaches a controller of the zone); a zone feeds another when the code of one of its domain modules imports one of the other's (`z`). The Build order tab
is a topological order of the `z` links (lanes, then names break ties): 18 drawn zones in 13 layers, no cycle, no feedback link; a test (`deps.test.tsx`) fails if a cycle comes back. Weights are numbers of modules.
`tests/domain/deps-fresh.test.ts` fails with "run `npm run deps:gen`" when the file is stale, `deps-generator.test.ts` runs the generator on a small synthetic project,
and CI runs `npm run deps:check`. The section *Dependencies* of the app draws this graph (lanes, nodes, edges, a side panel with the impacted sections and tests), a matrix, the zones and
figures, the build order with its cycle report and the tests impacted. The authored `SECTION_DEPS` registry is still stored with the case but is no longer shown (DEV-DEPS-ZONES).

**Test selection.** `npm run test:affected` selects the tests a change can reach and prints `files -> zones -> sections -> N of M test files (saved X%)`; the rule, the
cases that force the full suite and the validation (`npm run validate:affected`, mutation of sampled modules, recall must be 100%) are in [TEST_SELECTION.md](TEST_SELECTION.md).
The full suite stays mandatory before a merge and a release.

## 14. Process model (BPMN) — domain, reader / writer, export and the case's document (phases B1, B2, B3, B4 and B5 of [SPEC_BPMN.md](SPEC_BPMN.md))

`app/src/domain/process/` (zone `process-model`, input lane) holds the delivery process as a native BPMN 2.0 document. Since B3 (schema v3) the case
stores it, key `BPMN`, and nothing else of the scope: the engine reads the version 2 keys as views of it (`scopeOf`); since B2 the File menu exports it
and a controller reads `.bpmn` files into the node tree; since B4 the Process section imports them (one undoable step).

- **State model (B3, [SPEC_BPMN.md](SPEC_BPMN.md) § 6.4).** `CaseState.BPMN` is the node tree (plain objects / arrays, frozen by Immer, shared between
  versions). It replaces `selectedArtefacts`, `artefactsEdited`, `selectedRegArtefacts`, `regArtefactsEdited`, `phaseOff`, `selectedNorms`, `phaseSeq`,
  `regInclude`, `skillMap` (`SCOPE_KEYS`): `scopeOf(case)` (`domain/process/scope.ts`) derives them, memoised on the tree's identity, in the normal form
  of `normalKeys` (document order, complete edit lists, entries no element carries after the others). Every reader goes through it; an object without a
  document (a version 2 case handed to the engine by a tool or a test) is read by its own keys. The default case's document is built from the legacy
  default (`makeDefaultDoc`) and equals `catalog/defaultProcess.bpmn`.
- **Writes (B3).** `store/processEdit.ts`: `editProcess(draft, fn)` takes the tree the draft holds (`current`), lets a pure domain edit return the next one
  (structural sharing: `withAttrs`, `withChildren`, `editById`, `editWhere`, `appendChild`) and writes only the difference into the draft (`syncDraft`), so
  undo patches address an attribute or an element; `editScope(draft, fn)` runs a legacy scope rule on a copy of the keys and writes it with `withScope`.
  The `process.*` commands (`controllers/process.ts`) and the legacy scope commands (`scope.ts`, `frame.ts`, `artefacts.ts`, `verifyA.ts`) all write this
  way. A portfolio product overrides the whole document (`OVERRIDABLE_KEYS` has `BPMN`, F-B20); the address layer maps the node patches like any other.
- **Files (B3).** The document is XML text in every file and message: `store/persistence/bpmn/caseFile.ts` (`caseInFile`, `portfolioInFile` for the
  writers; `caseInStore`, `portfolioInStore` for the readers, through the B2 reader and its F-B10 checks; trees the readers built are trusted and not
  copied again). The text reads back into the identical tree, so an autosave record keeps its undo history. Version 2 shapes are read by
  `caseInStore` too (the migration 2 → 3, `fromSnapshot`, `readPortfolio`); `bpmn/legacy.ts` gives the legacy shape to the parameters workbook and the
  Overrides sheet, and applies a legacy patch to the tree.

- **Engine inputs (B5, [SPEC_BPMN.md](SPEC_BPMN.md) § 7.1).** `domain/process/engineInputs.ts` is the one owner of what the engine reads from the
  case's process: `caseViews` (the working artefacts are the document's activities, custom ones included), `caseLoopPairs` (rework loops: back flows,
  or the error boundary events of `readRework.ts` that replace them, D-B20), `caseSkillMap` (custom roles), `customActors` / `activitiesOfActor`
  (custom agents join `agentsOf`). An object without a document reads the catalogues. `domain/verifyA/processSummary.ts` owns what the outputs print of
  the process (results workbook Process sheet, report section 7, both only for a process with custom content).
- **Node tree** (`xml.ts`, `xmlWrite.ts`): the XML infoset as an immutable tree (element with namespace, local name, prefix, attributes in order,
  children; text; comment; namespace declarations kept as written). `serialize` is a faithful writer (no reformatting, white space is text nodes),
  so a tree serialises to the same bytes every time; `indent` adds the white space once, for the generated file. No DOM in the domain (the
  DOMParser-based reader is phase B2). `withAttrs` / `withChildren` / `mapElements` return the same object when nothing changes, so unchanged
  subtrees keep their identity (memoised views, small undo patches later).
- **Default process** (`buildProcess.ts` and its parts, `layout.ts`, `catalogue.ts`): the JSON catalogues mapped per spec § 3 / § 5.2 — phases as
  `subProcess` in sequence, Cross-cutting as an `adHocSubProcess` between a parallel fork and join, tasks typed by activity type (`userTask`,
  `manualTask`, `serviceTask`), parameters in `ac:activity` / `ac:supervision`, roles / regulatory team skills / agents as `resource` with
  `ac:actor`, `humanPerformer` / `performer` (with `resourceRef` children, as the OMG XSD requires), norms as `category` / `categoryValue`,
  deliverables as `dataObject` + `dataOutputAssociation`, loop pairs as back flows with `ac:rework`, and a deterministic BPMN DI layout (F-B14: lanes
  per team skill, phases left to right, Cross-cutting band at the bottom). `scripts/gen-default-process.ts` writes
  `src/domain/catalog/defaultProcess.bpmn` (the catalogue process with the default case's scope); `npm run process:check` (part of
  `npm run check`) and `tests/domain/process/default-process.test.ts` fail on any difference. The file follows the B0 profile and is valid for
  `tools/bpmn-validate.mjs` (OMG XSDs + `docs/bpmn/agentcase-bpmn-1.0.xsd` + profile; `tests/domain/process/validate.test.ts`); it is not
  imported by the application yet.
- **Typed reads** (`read.ts`, memoised on the document object): phases, activities, actors, flows, norms, diagram.
- **Views** (`views.ts`, `viewsCatalogue.ts`): from a document, exactly what the engine reads today — the version 2 scope keys, the artefact lists
  with the edited values, catalogue phases and phases with the ramp-up sequences, norms, loop pairs, the role → team-skill map. `processFromCase(case)`
  writes the case's keys onto the catalogue process (`ac:inScope`, list positions only when a list is not in document order, edited parameters on
  the activities themselves, entries no element can carry kept as `ac:unmatched` children of `ac:process`). `tests/domain/process/parity.test.ts` proves
  `viewsOf(processFromCase(c))` equals the version 2 keys on the 107 fixtures (as files and as opened by the store) and on every product of the
  portfolio fixtures.
- **Reader** (phase B2, `store/persistence/bpmn/read.ts`, tagged `exports`): XML text → node tree. The F-B10 checks run first on the raw text
  (`domain/process/security.ts`: size, DOCTYPE, entity, processing instruction, depth, element count, safe / reserved / duplicate ids, markup in text as
  a warning); their rule table `domain/process/securityRules.json` is the one `tools/bpmn-validate.mjs` reads, and codes and messages are identical
  file for file. Only then the browser's `DOMParser` (jsdom's in the tests) parses the text, and the DOM is converted to the infoset at once: the domain
  never sees a DOM. Prefixes, attribute order, namespace declarations, white space, comments and the text around the root are kept; CDATA becomes text.
  So `serialize(parse(x)) === x` for every file AgentCase writes, and is the canonical form of any other file (pass-through, F-B11; tested against
  `xmllint --c14n`). `controllers/bpmn.ts parseBpmnFile(file)` returns the tree and the diagnostics (codes of the validator plus `not-xml`, `not-bpmn`).
- **Export** (phase B2, `exportCase.ts`, `exportPortfolio.ts`, `partial.ts`, `bpsim.ts`): `exportDocument(case, { partial, bpsim, product })` is
  `processFromCase` + optional `ac:product` + optional in-scope filter (F-B3: out-of-scope activities, their deliverables, flows and DI removed,
  `ac:partial="true"`) + the BPSim 2.0 scenario (D-B5: `bpmn:relationship type="BPSimData"`, processing time = effort, probability of each rework
  flow, quantity = team FTE of each role; derived, replaced on each export, other BPSim data kept). The typed reader reads BPSim values only where
  the `ac:` value is absent. `collaborationDocument(products)` writes one file with one pool per product (ids prefixed `P1_`, `P2_`…, pools stacked in
  one diagram). Only the new parts are indented (the export is already in the writer's canonical indented form: `indent` of it changes nothing).
  `docs/bpmn/agentcase-bpmn-validate.xsd` imports the BPSim 2.0 schema (`docs/bpmn/omg/BPSim-2.0.xsd`), so exports validate it strictly.
  The File menu entry (`ui/shell/BpmnExport.tsx` → `controllers/bpmn.ts`) offers, for a portfolio, the product shown, one file per product or one file.
- **Process section, import, structure commands (phase B4, [SPEC_BPMN.md](SPEC_BPMN.md) § 8, § 9).** The app section 🧩 Process (BPMN)
  (`ui/sections/scope/process/`, scope group, `I-input`) shows the document: an SVG diagram drawn from its BPMN DI (`domain/process/drawing.ts`:
  shapes typed by element, an activity without a shape placed in its phase without moving the others; zoom / pan by keyboard and pointer are view
  state), the activity table that is its accessible alternative (filters, sort, scope check boxes), the selected activity's panel and the actor
  panel; view state lives in the section's own store (`view.ts`), never in the case. Import: `controllers/processImport.ts readProcessFile` (B2
  reader + `analyseImport`: an AgentCase file read with its `ac:` data, a foreign one through `importForeign.ts`: units = top-level sub-process, lane
  or process; roles = lane and performer names; what is not mapped counted by kind) → the preview (`previewImport`: mode, missing activities,

  AgentCase file = the file's tree, pass-through intact; otherwise a mapping onto the case's process: updates, appended activities with defaulted
  parameters from their phase and type (`importDefaults.ts`), new roles, the others kept, switched out of scope or removed in one pass).
